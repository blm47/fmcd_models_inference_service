# HadoopToS3Operator

Оператор и Spark driver предназначены для вашей библиотеки. Сохраняется структура:

```text
library/
├── utils/
│   └── general_utils.py           # существующая application_args_encoding
└── operators/
    ├── hadoop_to_s3_operator.py
    └── scripts/
        └── hadoop_to_s3_script.py
```

В этом репозитории каталог `airflow_operators` соответствует `operators` библиотеки.
`utils/general_utils.py` здесь отсутствует: используется существующая реализация
библиотеки, её копия или fallback не создаются. Сохранены исходные импорты Airflow;
для Airflow 2 поддержан импорт из провайдера Apache Spark.

## Контракт параметров

| Параметр | Поведение |
| --- | --- |
| `metrics_calc_variables` | Поля метаданных. `None` или `{}` отключают второй Spark job |
| `use_parquet_for_meta=True` | Запись метаданных в parquet |
| `no_delete_meta_file=False` | Для CSV используется Spark и именованный файл с накоплением строк |
| `no_delete_meta_file=True` | Для CSV используется GET → добавление строки → PUT через boto3 без DELETE |
| `dt_formatter` | Формат `load_start_time` и `finish_time`, по умолчанию `%Y%m%d%H%M%S` |
| `add_load_id=True` | Добавляет `load_id=...` к путям данных и обычной записи метаданных |
| `count_loaded_keys=True` | Подсчитывает parquet после успешной выгрузки данных и метаданных |
| `shard_column`, `num_shards` | Включают hash-шардирование при передаче обоих параметров |
| `shard_id_column="shard_id"` | Имя добавленной колонки номера шарда |
| `partition_by` | Дополнительные колонки разбиения результата |
| `repartition=1` | Число Spark-партиций перед записью, независимо от числа шардов |

Аргумент с опечаткой `mertics_calc_variables` сохранён для совместимости со старыми DAG.
Изменяемые словари копируются для каждого экземпляра оператора.

Пример дополнительных настроек при создании задачи:

```python
no_delete_meta_file=True,
use_parquet_for_meta=False,
dt_formatter="%Y-%m-%d %H:%M:%S",
count_loaded_keys=True,
shard_column="customer_mdm_id",
num_shards=9,
shard_id_column="shard_id",
repartition=36,
```

## Шардирование и GPU-инференс

Сначала выполняется Jinja-подстановка в исходном SQL, затем SELECT оборачивается:

```sql
SELECT
    _shard_source.*
    , pmod(xxhash64(_shard_source.`customer_mdm_id`), 9) AS `shard_id`
FROM (
    -- Исходный SQL после Jinja, без завершающей точки с запятой
) AS _shard_source
```

Поддержаны CTE, комментарии и точка с запятой внутри строковых литералов.
Несколько SQL statements, отсутствие ключа и конфликт имени добавляемой колонки
отклоняются до очистки выходного пути. Ключ используется с исходным типом без CAST:
для стабильного распределения между загрузками сохраняйте тип, число шардов и ключ.
NULL обрабатывается штатной функцией Spark xxhash64, случайное распределение не добавляется.

Запись выполняется через `repartition(36).write.partitionBy("shard_id")`.
Номер шарда не используется как ключ repartition: несколько задач могут писать
в один каталог. 36 — число Spark-партиций перед записью, а не число файлов и не
гарантия 36 одновременно работающих задач. Фактическая конкурентность зависит от ресурсов.

```text
<s3_path>/load_id=<load_id>/shard_id=0/part-....parquet
<s3_path>/load_id=<load_id>/shard_id=1/part-....parquet
...
<s3_path>/load_id=<load_id>/shard_id=8/part-....parquet
```

`customer_mdm_id` остаётся в Parquet. Колонка `shard_id` хранится в имени каталога,
а не внутри файлов. Без shard_column и num_shards сохраняется обычная запись.
Метаданные не шардируются; overwrite заменяет текущий путь загрузки целиком.

Для следующего `GPUModelInferenceOperator` задайте `partition_by="shard_id"`,
`n_shards=9` и `s3_input_prefix` равным пути текущей загрузки, без `shard_id=...`.
Если `add_load_id=True`, удобно передать загрузчику явный шаблонизированный `load_id`
и использовать то же значение в префиксе GPU-оператора.

Пустые шарды не создаются. GPU-оператор перебирает все N префиксов, поэтому при
отсутствующем шарде текущий сервис вернёт ошибку отсутствующего входа. Обработка
пустых шардов в GPU-операторе не менялась в рамках этой доработки.

Загрузка данных выполняется первой, метаданных — второй. Второй job никогда
не очищает путь данных, даже при `clear_s3_path=True`. Оба используют один load_id
и одну метку начала загрузки. `connection_timeout` передаётся оператору в секундах,
а driver преобразует его в миллисекунды для S3A, как в актуальном оригинале.

## XCom и подсчёт файлов

- `mark_loaded_at` — UTC ISO timestamp непосредственно перед первым Spark job.
- `cnt_loaded_keys` — число `.parquet` под `s3_path/load_id=<текущий load_id>/`,
  включая вложенные каталоги шардов. `_SUCCESS` и соседние load_id исключаются.
- При ошибке подсчёта сохраняется `-1` и сообщение `warn`; выгрузка остаётся успешной.
- При `count_loaded_keys=False` обращения к S3 для подсчёта и XCom `cnt_loaded_keys` нет.

При `add_load_id=False` считаются parquet всего `s3_path/`. Если этот путь используется
для нескольких загрузок в режиме append, отличить файлы конкретной загрузки по одному
префиксу невозможно. Счётчик показывает итоговое содержимое префикса, а не число новых файлов.

## Метаданные

`inc_rowcount` считается через Spark `count()` только если запрошено его вычисление
значением `"None"`. Это число строк результата SQL, а не количество файлов.
Переданное числовое значение сохраняется. `start_time` берётся из `load_start_time`;
`finish_time` вычисляется после подсчёта строк. Поля `start_time_sumk`, `finish_time_sumk`,
`status_sumk` сохранены в наборе по умолчанию. Как в присланном коде, дополнительная
логика вычисления SUMK-полей не добавляется.

В режиме `no_delete_meta_file=True` намеренно сохранён путь оригинала:
`s3_meta_path.replace('/', '')/<последняя часть object_name>.csv`.
Например, `meta/table` и `db.results` дают `metatable/results.csv`.
`load_id` в этот путь не добавляется. CSV сохраняется с заголовком, как в оригинале.
Учётные данные берутся из закодированного `spark.app.oper.s3_password`.

Обычная CSV-ветка сохраняет `<meta_path>/<имя объекта>.csv` и добавляет новую строку
к существующим метаданным. Объединённый результат записывается во временный каталог,
затем заменяет именованный CSV. Ошибка записи не удаляет старый файл; при ошибке
публикации временный результат остаётся для восстановления. Это не атомарная замена
в S3. Для обоих способов записи CSV не допускаются параллельные обновления одного
файла: исходный контракт GET/PUT и Spark rename не защищает от потери обновлений.

Подсчёт файлов и CSV через boto3 сохраняют настройки подключения оригинала:
`use_ssl=True`, `verify=False`, `signature_version="s3v4"`, адресация `path`.
Это отдельные клиенты библиотеки, не ENV-конфигурация GPU-сервиса.

Логи оператора идут через `self.log` Airflow. Spark driver получает один logger
Spark при запуске и передаёт его функциям; используются `info`, `warn`, `error`.
Полные аргументы и учётные данные в лог не выводятся.

Тесты проверяют транспорт аргументов, XCom, пагинацию и отбор parquet,
метаданные, обе CSV-ветки, порядок замены файла, SQL-обёртку после Jinja,
валидацию шардирования и независимый repartition. Запуск Spark/S3 в рабочем окружении
и наличие вашей `application_args_encoding` проверяются при установке в библиотеку.
