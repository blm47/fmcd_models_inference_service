# MODEL-001: общий ModelBundle и загрузка на время задачи

Статус: ТЗ с уточнениями пользователя от 2026-09-13. Реализация не начата.
Заменяет предложение загрузки моделей при старте из fmcd-invest-review.md.

## Цель

Подключать уникальные pipeline через подклассы ModelBundle. Один экземпляр класса
создаётся на одну задачу. Pipeline может содержать несколько моделей, preprocessing
и postprocessing. Общая инфраструктура не знает о CatBoost, ProdSchema и формулах модели.
На поде выполняется одна задача за раз, без кэширования весов между задачами.

## YAML

```yaml
models:
  - name: credit_cards
    backend: fmcd_cc_dc
    artifacts_dir: artifacts/credit_cards
    id_cols: [customer_mdm_id, partition_report_dt]
    device: cuda:0
    infer_batch_size: 500
    parquet_read_chunk_size: 5000
  - name: FMCD_INVEST
    backend: fmcd_invest
    artifacts_dir: artifacts/FMCD_INVEST
    id_cols: [counterparty_id, report_dt]
    device: cpu
    infer_batch_size: 4096
    parquet_read_chunk_size: 8192
```

Все шесть полей пользователя обязательны. Дополнительно согласован backend:
name идентифицирует экземпляр в API, backend выбирает класс pipeline. Несколько
экземпляров с разными артефактами могут использовать одну реализацию.
Каждый новый уникальный pipeline получает свой backend; модели с общей логикой,
как ДК и КК, переиспользуют один backend с разными настройками и артефактами.
Значения размеров INVEST — начальные для измерений, а не оценка производительности.

infer_batch_size — максимум строк одного predict_batch, передаваемых на заданный
device (CPU или GPU). Это новое имя ранее предложенного gpu_infer_batch_size;
два отдельных параметра или alias для него не вводятся.
parquet_read_chunk_size — максимум строк чанка reader, не гарантия размера row group
или пика RAM. Чанк может быть меньше infer-батча; остаточный батч может содержать одну строку.
Необязательный options допустим для специфики backend, например catboost_thread_count.
Общие параметры в options не дублируются. Настройки device/batch/chunk больше не глобальные.
При недоступном CUDA нельзя молча переходить на CPU.

## Лёгкий каталог вместо загруженных моделей

На старте читается только YAML моделей. Ни model.json, ни схемы, ни списки
обязательных колонок, ни другие артефакты моделей не читаются.
При новом POST /infer читается небольшой model.json только запрошенной модели.
В model.json: format_version, artifact_version, required_columns (признаки без ключей),
output_columns (результаты без ключей), files (относительные пути к артефактам).
В нём нет больших словарей, числовых массивов и весов. Подкаталоги артефактов разрешены.
id_cols из YAML добавляются к входному контракту автоматически.

Manifest генерируется при упаковке из исходных схем модели. Для legacy — из schema.json
и текущей схемы выходов; для INVEST — из объединения признаков двух веток и 12 выходов.
Backend при load сверяет manifest с фактическими артефактами. Добавление типов в контракт
допустимо, но универсальная система статистической валидации данных вне POC.

app.state.models хранит ModelSpec (настройки YAML + backend), не живые ModelBundle.
Контракт из manifest читается на время запроса и не добавляется в постоянный каталог.
Реестр backend → путь импорта/фабрика не создаёт экземпляры; тяжёлые импорты ленивые.
При старте запрещены torch.load, CatBoost.load_model, большие preprocessing-таблицы
и CUDA-инициализация ради моделей. Проверяется структура YAML и известность backend;
проверка наличия и содержимого файлов переносится на запрос/load соответственно.

POST /infer сохраняет проверку имени, входных колонок, количества строк и выходного
prefix, но использует контракт, прочитанный для выбранной модели, без загрузки весов.
Проверка существующего идемпотентного запроса предшествует чтению manifest:
повторный опрос прежней заявки не требует повторной проверки артефактов.
404 для неизвестной модели/входа и 422 для отсутствующих признаков сохраняются.
Отсутствующий или повреждённый manifest известной модели — ошибка конфигурации
сервера (500 с понятной диагностикой в логе), задача не ставится в очередь.
Несовместимый checkpoint выявляется при load и переводит уже принятую задачу в FAILED.
202 означает приём в очередь, не успешную загрузку модели.

Каталог артефактов неизменен до завершения принятых задач; все поды одного name
исполняют одну версию. В POC rollout — после дренирования очереди. Hot reload и
смена версии в непустой очереди без фиксации версии в задаче не поддерживаются.

## Интерфейс ModelBundle

```text
ModelBundle(spec, logger)                         # лёгкий конструктор
load() -> None                                   # загрузка полного pipeline
predict_batch(frame, check_shutdown) -> DataFrame # pre + infer + post
close() -> None                                  # освобождение ресурсов
```

Все три метода реализуются подклассом. close идемпотентен и работает после частично
неудачного load. Конструктор не загружает ресурсы. Отдельные preprocess/postprocess
могут быть внутренними методами, но не обязательными точками расширения.

Контракт predict_batch:
- Одна выходная строка на входную, сохранены порядок и значения id_cols.
- Вход не изменяется, Pandas index не используется как бизнес-ключ.
- Схема и типы результата стабильны между батчами, включая батч из одной строки.
- Набор выходов соответствует manifest, ошибки пробрасываются worker.
- Словари и статистики берутся из обучения, не рассчитываются на scoring-батче.
- check_shutdown вызывается между дорогими стадиями и внутренними подбатчами.
- ModelBundle не управляет Airflow, S3, TaskStore и progress; logger получает снаружи.

POC предназначен для построчных pipeline. Глобальные агрегации, сортировки, fit
на всём dataset и изменение количества строк требуют отдельного контракта.

## Lifecycle worker

```text
claim → RUNNING → heartbeat → проверка отмены и выходного prefix
  → создать экземпляр → load
  → читать Parquet чанками parquet_read_chunk_size
      → делить чанк на infer_batch_size
      → predict_batch → проверка ключей/числа строк/схемы
      → собрать результаты только текущего чанка
      → проверка отмены → запись чанка → progress
  → FINALIZING → _SUCCESS → DONE
finally: close → убрать ссылки → завершить heartbeat → освободить слот
```

close находится в finally вокруг load и расчёта. Существующие гарантии сохранения
статуса при ошибках S3 сохраняются. Следующая задача не начинается до завершения
close, даже если предыдущая уже получила терминальный статус от монитора.
Две последовательные задачи одной модели означают две загрузки и две выгрузки.
Writer получает чанк, а не создаёт файл на каждый маленький infer-батч.
Нельзя накапливать dataset или результаты всех чанков в памяти.

## Освобождение памяти и ошибки

Backend освобождает веса, encoder, словари, буферы, файлы и собственные потоки.
После снятия ссылок для PyTorch допустимы gc.collect и очистка CUDA cache один раз
на завершение задачи. empty_cache в каждом legacy-батче убрать после проверки памяти.
Исключения и внешние ссылки на результаты не должны удерживать прежний pipeline.

Освобождение объектов не гарантирует возврат RSS/VRAM к стартовому уровню: allocator
и CUDA runtime могут удерживать память. Приёмка — отсутствие живых весов предыдущей
модели и неограниченного роста на серии задач. Пользователь подтвердил, что этого
достаточно. Исполнение остаётся в текущем процессе; отдельный процесс на задачу
и требование возврата RSS/VRAM точно к стартовому уровню в эту доработку не входят.

- Частичная ошибка load, ошибка inference/write, отмена, shutdown: обязательно close.
- Ошибка close логируется отдельно и не маскирует исходную причину.
- Если DONE уже опубликован, ошибка close не превращает результат в FAILED.
  Под перестаёт брать задачи и считается неготовым к исполнению до перезапуска.
- SIGKILL не гарантирует finally: применяется существующий монитор heartbeat,
  ресурсы завершённого процесса освобождает ОС.
- Отмена кооперативная, загрузчик не обязан уметь прерывать один нативный вызов.

## Прогресс, heartbeat и настройки потоков

Статусы API сохраняются. RUNNING включает load; новые статусы для загрузки не нужны.
Heartbeat работает и во время загрузки. Логи содержат модель/task_id, начало/конец
load и close, длительности, прогресс строк. processed_rows обновляется после записи чанка.
ETA до первого чанка отсутствует; оценивает оставшуюся обработку по текущей метрике
pipeline, не включает load/close и не обещает время до DONE.

Текущий progress_timeout_sec включает время load: при rollout подобрать значение
больше ожидаемой загрузки и самого долгого чанка. Heartbeat не сбрасывает таймаут
отсутствия прогресса. Отдельный load timeout — возможная последующая настройка.
Не менять глобальные torch thread settings бесконтрольно на каждой модели:
общие лимиты задаёт окружение процесса, локальные — API конкретной библиотеки.

## Миграция

1. Зафиксировать baseline входов/выходов действующих моделей.
2. Ввести ModelSpec, manifest и абстрактный ModelBundle.
3. LegacyFMCDModel переносит нынешние loader, ProdSchema, frequency encoding,
   калибраторы и формулы, сохраняя выходные имена и значения.
4. Внешнее разбиение на infer-батчи переносится в worker; predict_batch legacy
   выполняет один батч, без второго общего цикла и полного all_results.
5. API/validation читают контракт выбранной модели при запросе; startup читает
   только YAML и больше не вызывает load_all_models или чтение manifest.
6. Consumer получает каталог спецификаций, worker — lazy lifecycle с finally.
7. Обновить все YAML репозитория и manifests. Удалить глобальные device/batch/chunk
   и старые специфичные пути из общего ModelConfig, перенести пути в manifest.
8. Регрессия, измерение памяти и проверка очереди/Airflow.
9. FMCDInvestModel — после получения комплектных артефактов и эталона.

В репозитории подтверждён действующий credit_cards. Другие внешние конфигурации
пользователь предоставляет отдельно; все экземпляры прежней архитектуры мигрируют
на legacy_fmcd. Отсутствие INVEST-артефактов не блокирует базовый интерфейс и legacy.
Не держать два источника настроек с неочевидным приоритетом: новый YAML — явная миграция.
Если нужен переходный адаптер старого YAML на один релиз, согласовать отдельно.

INVEST сохраняет общий выход CatBoost F/C, две ветки на одном батче и 14 выходных
колонок. Уникальность ключей и эквивалентность notebook merge подтвердить до переноса.

## Приёмка

- Startup и POST /infer не вызывают load ни одного backend.
- Startup не читает manifest, схемы и обязательные колонки ни одной модели.
- Новый запрос читает контракт только выбранной модели; повтор принятого запроса
  возвращается по ключу идемпотентности без обращения к артефактам.
- Проверено переиспользование backend разными именами моделей и каталогами артефактов.
- Проверен порядок create/load/predict/close, отсутствие перекрытия задач и кэша.
- Проверены partial load failure, inference/write failures, отмена, shutdown,
  ошибка close без потери первоначального исключения.
- Per-model размеры и device реально используются; проверены остаточный батч,
  одна строка и чанк меньше батча.
- Legacy сохраняет ID, колонки и результаты в заранее согласованной погрешности;
  нет скрытых изменений обработки пропусков и калибровки.
- Сохраняются API, идемпотентность, очередь, reschedule, шарды, ETA и _SUCCESS.
- Реальная серия разных моделей не даёт растущего потребления памяти после прогрева;
  измерены CPU RSS и GPU allocated/reserved. Мок-тесты это не доказывают.
- INVEST сравнивается с эталоном по промежуточным стадиям и окончательным выходам.
- Для следующего уникального pipeline нужны класс, одна регистрация, каталог
  с manifest и запись YAML; worker, API и S3 менять не требуется.

## Зафиксированные решения и оставшиеся уточнения

Согласовано: backend переиспользуется для общей логики; на старте только YAML;
контракт входа читается при запросе, веса — только после захвата задачи worker;
экземпляр на задачу, текущий процесс с close и без накопления моделей в памяти.
Размер батча устройства называется infer_batch_size, отдельно от parquet_read_chunk_size.
Остаётся уточнить при необходимости: переходный старый YAML и наличие среди новых
моделей непострочных pipeline. Эти вопросы не меняют согласованный lifecycle.
