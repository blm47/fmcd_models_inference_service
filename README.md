# FMCD Inference Service

FastAPI-сервис инференса FMCD-моделей с фоновой обработкой, потоковым S3 I/O
по ПРЕФИКСАМ (Spark-style: _SUCCESS + part-*.parquet) и GPU (H100).

## Важно: контракт S3-путей
`s3_input_path` и `s3_output_path` в запросе `/infer` - это ПРЕФИКСЫ (папки),
а не пути к одиночным файлам:
- `s3_input_path` - папка, куда Spark сохранил DataFrame (
  `_SUCCESS` + множество `part-*.parquet`). Сервис читает ВСЕ part-файлы
  под этим префиксом как единый датасет и режет их на чанки по `chunk_size`
  строк (границы чанков не совпадают с границами part-файлов).
- `s3_output_path` - папка, куда сервис пишет результат: по одному
  `part-{idx:05d}.parquet` на каждый chunk_size строк, и `_SUCCESS` маркер
  после успешного завершения (маркер НЕ пишется при ошибке/аборте - это
  сигнал для downstream, что выгрузка неполная).

## Структура
- `app/main.py` — точка входа, lifespan-загрузка всех моделей на GPU
- `app/api/` — роуты `/infer`, `/tasks/{id}/status`, `/tasks/{id}/abort`
- `app/models/` — ModelBundle, загрузка артефактов (loader.py), батчевый инференс, валидация фич
- `app/tasks/` — общее состояние задач в S3, cancellation, TaskManager
- `app/storage/s3_client.py` — потоковое чтение/запись parquet ПРЕФИКСОВ через pyarrow.dataset
- `fmcd/` — существующий пакет пользователя (schema/data/model), копируется как есть
- `artifacts/<model_name>/` — веса и препроцессинг-артефакты каждой модели, вшиты в образ
- `configs/models.yaml` — список моделей + инференс/S3(имена env)/task конфигурация
- `deploy/` — Dockerfile и Helm chart

## Конфигурация через env
Все значения S3 (эндпоинт, ключи, бакеты) читаются из переменных окружения,
имена которых заданы в `configs/models.yaml -> s3.*_env`. Helm прокидывает
сами значения через `env:` в Deployment (ConfigMap для несекретных значений,
Secret для access/secret key).

## Статусы задач: два постоянных объекта S3

Все экземпляры Deployment используют только `task_store.state_key` и
`task_store.lock_key` в выходном бакете. По умолчанию это
`_system/fmcd_models/task_state.json` и `_system/fmcd_models/task_state.lock`.
Они создаются при старте, если ещё отсутствуют, и затем перезаписываются.
Новые объекты на задачу и операции DELETE для статусов не требуются. Файлы
результата инференса (`part-*.parquet`, `_SUCCESS`) живут отдельно от task tracker.

В `task_state.json` хранится словарь с одним текущим состоянием каждой задачи.
Прогресс, heartbeat и финальный статус заменяют предыдущие значения той же
записи. История промежуточных состояний не создаётся. Если на сервере включено
версионирование объектов, сервер может сохранять прежние версии перезаписей;
их удаление требует настройки хранения на самом S3.

Захват общего lease-lock использует локальный mutex, уникальный токен каждой
попытки, подтверждение через 2 секунды и случайную задержку перед повтором.
Владелец и остаток lease перепроверяются перед записью; освобождение проверяет
токен владельца. Чтение статусов не захватывает lock и ничего не записывает.
Это best-effort координация: без условной записи S3 остаётся окно гонки между
проверкой и перезаписью. Возможны потеря обновления и задержка/потеря отмены.
Численная гарантия вероятности столкновения не предоставляется. Долгие сетевые
паузы и рассинхронизация часов подов также влияют на lease; часы должны быть
синхронизированы. Таймауты клиента task tracker: подключение 5 с, чтение 10 с,
максимум 2 попытки запроса.

Deployment может иметь от 1 до 3 подов с произвольными именами; закреплённые
номера подов не нужны. В каждом поде запускается один процесс Uvicorn, который
выполняет не более одной задачи одновременно. При обновлении с прежней схемы
lock сначала остановите все старые экземпляры: смешанная работа старого кода,
который безусловно освобождал lock, с новым протоколом токенов не поддерживается.

## Heartbeat, отмена и очистка

Во время выполнения отдельный поток обновляет `heartbeat_at` независимо от
чанков инференса. В простое heartbeat не записывается. Задачи, от которых нет
heartbeat дольше `heartbeat_timeout_sec`, исключаются из `/tasks/active`;
чтение отдельного статуса показывает `executor_alive: false`. Для старых
записей без heartbeat используется `updated_at`. Просроченный heartbeat означает
отсутствие подтверждения жизни исполнителя: статус не переводится необратимо
в `FAILED`, поскольку временная недоступность S3 или зависание могут закончиться.
Автоматический перехват задачи другим подом не выполняется.

Запрос отмены с любого пода сохраняет `cancel_requested` и `ABORTING` в общем
словаре. Исполнитель проверяет S3 и останавливается на ближайшей проверке между
операциями/батчами. Текущий вызов
GPU или S3 не прерывается принудительно. После обработки всех чанков задача
переходит в `FINALIZING`: новые запросы отмены уже отклоняются, затем публикуется
`_SUCCESS` и сохраняется `DONE`. При принятой отмене сохраняется `ABORTED`,
маркер успешного завершения не публикуется. Уже записанные части результата
при ошибке/отмене остаются в S3, поскольку права DELETE отсутствуют. Для каждого
запуска используйте новый выходной префикс, чтобы старый `_SUCCESS` не обозначал
неполный новый результат как успешный.

Если результат уже опубликован, запись `DONE` повторяется до трёх раз. При
неудаче статус может остаться `FINALIZING` с просроченным heartbeat; в логах
будет ошибка доставки статуса. Такой результат не переводится в `FAILED`.
Запись результата и JSON статуса не являются общей транзакцией S3.

Очистка запускается в фоне каждые `cleanup_interval_sec`, в том числе в простое.
Истёкшие записи удаляются из словаря с перезаписью того же `task_state.json`;
число объектов остаётся постоянным. Срок `retention_months` отсчитывается от
завершения финальной задачи, а для заброшенной — от последнего heartbeat
исполнителя (для старых записей — от `updated_at`). Месяц здесь равен 30 суткам.
Задачи с живым исполнителем не удаляются из-за давнего времени запуска.
Если очищать нечего, проверка не захватывает lock и не пишет в S3.

Параметры задаются в `configs/models.yaml -> task_store` либо Helm
`values.yaml -> taskStore`; переменные окружения имеют приоритет:

| YAML | Helm | Переменная окружения | По умолчанию |
| --- | --- | --- | --- |
| `backend` | `backend` | `TASK_STORE_BACKEND` | `s3` |
| `state_key` | `stateKey` | `TASK_STORE_STATE_KEY` | `_system/fmcd_models/task_state.json` |
| `lock_key` | `lockKey` | `TASK_STORE_LOCK_KEY` | `_system/fmcd_models/task_state.lock` |
| `lease_seconds` | `leaseSeconds` | `TASK_STORE_LEASE_SECONDS` | 60 |
| `wait_timeout_sec` | `waitTimeoutSec` | `TASK_STORE_WAIT_TIMEOUT_SEC` | 300 |
| `poll_interval_sec` | `pollIntervalSec` | `TASK_STORE_POLL_INTERVAL_SEC` | 1 |
| `retention_months` | `retentionMonths` | `TASK_STORE_RETENTION_MONTHS` | 6 |
| `heartbeat_interval_sec` | `heartbeatIntervalSec` | `TASK_STORE_HEARTBEAT_INTERVAL_SEC` | 30 |
| `heartbeat_timeout_sec` | `heartbeatTimeoutSec` | `TASK_STORE_HEARTBEAT_TIMEOUT_SEC` | 180 |
| `cleanup_interval_sec` | `cleanupIntervalSec` | `TASK_STORE_CLEANUP_INTERVAL_SEC` | 3600 |

Интервалы должны быть конечными положительными числами, срок хранения — целым
числом месяцев больше нуля, а `heartbeat_timeout_sec` — больше интервала
heartbeat. Таймаут жизни исполнителя выбирайте с запасом на конкуренцию за
lock и сетевые задержки: он определяет и время исчезновения умерших задач из
активных, и риск временно скрыть работающую задачу при проблемах S3.

Проверки task tracker без загрузки моделей/GPU:

```bash
python -m unittest discover -s tests -v
```

## Локальный запуск
```bash
pip install -r requirements.txt
export S3_ENDPOINT_URL=... S3_BUCKET_IN=... S3_BUCKET_OUT=... S3_ACCESS_KEY=... S3_SECRET_KEY=...
uvicorn app.main:app --reload
```

## Сборка образа
```bash
docker build -f deploy/Dockerfile -t fmcd-inference-service:0.1.0 .
```

## Деплой через Helm
```bash
helm install fmcd-inference deploy/helm -f deploy/helm/values.yaml
```
