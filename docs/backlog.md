# Бэклог

## MODEL-001 — Общий ModelBundle и загрузка на время задачи

Статус: реализация начата 2026-09-13 в ветке `feature/model-001-model-bundle`.
Этапы 1–3 реализованы на уровне кода и синтетических тестов: общий контракт,
адаптер карт, per-task load/close, новый YAML, проверки данных в worker.
Движки, их вспомогательный код и модельные классы разнесены по каталогам backend.
INVEST пока заглушка. Метрики этапов заменены опциональной посекундной утилизацией в памяти worker; приёмка
с настоящими весами и реальные замеры остаются открытыми. Совместимость с прежней
архитектурой исключена: препрод разворачивается с нуля.
План этапов, проверки и ограничения: [план реализации](model-bundle-implementation.md).
Приоритет: до подключения следующих четырёх уникальных pipeline.
Полное ТЗ и порядок миграции: [ModelBundle](model-bundle-spec.md).
ТЗ имеет приоритет над первоначальным предложением startup-загрузки.
Разбор прототипа: [FMCD_INVEST](fmcd-invest-review.md).

Проблема: текущие loader, ModelBundle, валидация входов и worker рассчитаны на
один формат FMCD. FMCD_INVEST требует CatBoost, собственного preprocessing,
нейросетевого stacking и других выходных колонок.

Объём POC:
- Общий ModelBundle: load / predict_batch / обязательный идемпотентный close.
- На старте YAML и вызов заглушки скачивания файлов каждой модели на диск пода;
  без разбора схем и загрузки весов в память.
- POST /infer только принимает заявку; входы, колонки и число строк проверяет
  worker после загрузки модели и артефактов. Ошибка проверки даёт FAILED.
- Загрузка только после захвата задачи, выгрузка после каждой задачи, без кэша.
- Реестр backend → класс; уникальный backend на новый pipeline, переиспользование
  для общей логики (например, ДК/КК); один корневой каталог артефактов на модель.
- Выполнение в текущем процессе с close, без накопления объектов между задачами;
  отдельный процесс и строгий возврат RSS/VRAM к исходному уровню не требуются.
- Адаптер текущего FMCD без изменения результатов и отдельный FMCDInvestRunner.
- YAML на модель: name, backend, artifacts_dir, id_cols, device,
  infer_batch_size, parquet_read_chunk_size; специфичные параметры через options.
  infer_batch_size — батч для заданного device, CPU или GPU.
- Worker и API используют интерфейс; S3, очередь, прогресс, отмена и публикация
  результата остаются общей инфраструктурой.
- SQL первого этапа: выборка, типы, подтверждённый zero-fill; обучение preprocessing
  не выполняется при scoring. Полный preprocessing в SQL — последующая оптимизация.

Критерии готовности:
- Startup/API не загружают модели; load/close проверены при успехе, ошибках и отмене.
- Следующая задача не начинается до выгрузки предыдущей; память проверена серией запусков.
- Существующая модель даёт прежние результаты; оба backend подключаются конфигурацией.
- FMCD_INVEST совпадает с эталоном по промежуточным стадиям и конечным 14 колонкам
  в согласованной погрешности; обработка чанками сохраняет ключи и число строк.
- Проверены null/NaN, неизвестные категории, порядок признаков, границы и округление.
- Сохраняются работа без шардов и с ними, reschedule, отмена, ошибки, ETA и _SUCCESS.
- При `calc_utilization=true` worker считает в памяти min/max/mean/median утилизации CPU/GPU (%), RAM/GPU_RAM (% и МБ),
  измеренной раз в секунду; итог выводится в logger после close.

Зависимости: полный SQL/ноутбук, комплект артефактов, подтверждённый контракт ключей,
эталон и допуски. Не включать в POC Triton, hot reload или универсальный DAG pipeline.

## MODEL-002 — Скачивание моделей и артефактов через API model registry

Статус: добавлено 2026-09-13; в MODEL-001 реализована startup-заглушка
`download_model_artifacts(name, artifacts_dir, logger)`.

Проблема: сейчас комплект модели размещается в репозитории и включается в образ
при сборке. Требуется получать его из model registry через API.

Объём:
- При каждом старте пода скачать каждую настроенную модель и полный комплект
  артефактов в локальный `artifacts_dir` до запуска consumer и готовности пода.
- Загрузка файлов на диск отделена от загрузки весов в RAM/VRAM: последняя
  выполняется worker на время задачи.
- Реализовать API-клиент вместо заглушки, согласовав endpoint, авторизацию,
  идентификатор/версию модели и формат выдачи файлов.
- Проверять комплектность и целостность скачивания; незавершённая загрузка
  не должна становиться рабочим каталогом. Ошибка скачивания прерывает startup.
- Удалить необходимость включения комплектов моделей в исходники и образ,
  подготовить writable каталог и параметры Kubernetes для скачивания.
- Зафиксировать одну версию модели для всех подов; обновлять после дренирования очереди.

Пока заглушка только логирует использование локальных файлов. Реальных HTTP-запросов
и фиктивного подтверждения скачивания нет. Контракт внешнего API ещё не предоставлен.
