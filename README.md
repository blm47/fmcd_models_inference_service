# FMCD Inference Service

FastAPI-сервис выполняет GPU-инференс над parquet из S3. Любой под принимает
заявки, свободные поды забирают их из общей очереди. На каждом поде работает
один процесс Uvicorn и один последовательный GPU worker.

Подробные [диаграммы архитектуры и взаимодействия с Airflow](docs/inference-architecture.md)
сохранены вместе с редактируемыми исходниками Mermaid.

## Документация API (Swagger)

После запуска сервиса доступны:

- `/docs` — Swagger UI с описаниями методов, параметров, статусов и ошибок.
- `/redoc` — альтернативное представление документации.
- `/openapi.json` — автоматически сформированная схема OpenAPI для экспорта
  и генерации клиентов.

При локальном запуске откройте `http://localhost:8080/docs`.
В Kubernetes используйте тот же адрес сервиса, что и для `/infer`, добавив `/docs`.
Кнопка **Try it out** отправляет настоящий запрос: `POST /infer` создаёт задачу,
а `POST /tasks/{task_id}/abort` запрашивает отмену.

FastAPI строит схему из зарегистрированных маршрутов и Pydantic-моделей.
После изменения кода и перезапуска сервиса документация обновляется автоматически.
При добавлении API задавайте `response_model`, `summary`, docstring и `responses`
у маршрута, а описания и примеры полей — через `Field` в `app/api/schemas.py`.
Текстовые пояснения поведения нужно актуализировать вместе с реализацией.
Отдельную копию OpenAPI вручную поддерживать не нужно.

Swagger UI и ReDoc доступны на работающем сервисе. Статический Markdown-снимок
не хранится; актуальная схема доступна через `/openapi.json`.
Swagger UI и ReDoc загружают JS/CSS из CDN, `/openapi.json` этого не требует.

## Вызов из Airflow

[HadoopToS3Operator](docs/hadoop-to-s3-operator.md) запускает Spark job для подготовки данных,
опциональную выгрузку метаданных и подсчёт parquet текущей загрузки.

Готовый [GPUModelInferenceOperator для Airflow 2.6.3](docs/airflow-operator.md)
отправляет заявки без авторизации через `service_url` и ждёт в режиме `reschedule`.
Поддерживает один префикс или шарды `shard_id_column=0..num_shards-1`.

1. Оператор hadoop_2_S3 в Airflow запускает через spark-submit подготовку входного префикса: `_SUCCESS` и `part-*.parquet`.
   Во время ожидания в очереди и расчёта входные данные должны оставаться неизменными.
2. Отправляет `POST /infer` со стабильным ключом **одной попытки расчёта**:

   ```json
   {
     "idempotency_key": "dag_id/run_id/task_id/map_index/attempt-1",
     "model_name": "fmcd_credit_cards",
     "s3_input_path": "s3://input-bucket/data/run-1",
     "s3_output_path": "s3://output-bucket/results/run-1"
   }
   ```

3. После сохранения заявки API возвращает `202`, `task_id`, `QUEUED`,
   `pod_id: null` и `total_rows: null`. Worker проверяет вход и сохраняет число
   строк после старта задачи. Ошибка входа или колонок даёт `FAILED`.
   Занятость принимающего пода не мешает приёму.
4. Sensor опрашивает `GET /tasks/{task_id}/status` через любой под.
5. При `DONE` оператор S3_2_Hadoop запускает Spark job, читающий выходные parquet
   из S3 и записывающий их в Hadoop. Данные через Airflow не проходят. Сервис публикует `_SUCCESS`
   перед сохранением `DONE`.
6. После `FAILED` или `ABORTED` Airflow очищает **только выходной префикс
   расчёта**, включая `_SUCCESS`, и отправляет новую заявку с **новым ключом**.
   Инференс новой попытки начинается с первой строки.

Повтор HTTP-запроса после потери ответа использует прежний ключ и прежние
параметры: API вернёт ту же задачу, даже если расчёт уже завершился. Повтор
с тем же ключом и другими параметрами получает `409`. Ключи сохраняются
вместе с задачами: в S3 до истечения retention, в PG без автоматической очистки.

Выходной префикс должен быть непустым путём внутри `S3_BUCKET_OUT`,
входной — внутри `S3_BUCKET_IN`. Пересечение входа и выхода, выход в корень
бакета и пересечение выхода с системным файлом запрещены. API проверяет параметры
и ставит задачу в очередь, не читая входные данные и содержимое выхода.
Наличие parquet или `_SUCCESS` в выходе завершает принятую задачу как `FAILED`
при проверке worker перед началом записи. Незавершённые задачи резервируют свои выходные
префиксы, включая вложенные пути.

**При backend=s3 нельзя очищать выходной бакет целиком:** в нём хранится общая очередь
`_system/fmcd_models/task_state.json`. Права DELETE сервису не требуются.

## Статусы и отмена

```text
QUEUED → RUNNING → FINALIZING → DONE
   │        ├────────────────→ FAILED
   │        └→ ABORTING ─────→ ABORTED
   └────────────────────────→ ABORTED
```

Ошибка публикации результата в `FINALIZING` также может завершить задачу
как `FAILED`. После публикации результата worker повторяет сохранение `DONE`.
Если проверка таймаута уже сохранила `FAILED`, поздний ответ worker не заменит его на `DONE`.

`POST /tasks/{task_id}/abort` сразу отменяет ожидающую задачу. Для выполняющейся
задачи сохраняет `ABORTING`; worker проверяет отмену между чанками.
`FINALIZING` уже не принимает отмену: API возвращает `409`.

## Аварии, таймауты и shutdown

Kubernetes вызывает `/healthz/readiness`: ручка проверяет очередь независимо от
занятости GPU и переводит просроченные RUNNING, ABORTING и FINALIZING в FAILED.
Причина `task_timeout` означает отсутствие обновлений `last_modified` дольше
`task_timeout_sec` (по умолчанию 1800 секунд). Отдельного потока monitor_queue нет.

Heartbeat обновляет `last_modified` каждые `heartbeat_interval_sec` (30 секунд),
в том числе во время долгого load/infer/I/O. Опрос статуса и запрос отмены
RUNNING-задачи не продлевают таймаут. При работающем heartbeat отсутствие прогресса
само по себе не завершает задачу. ETA остаётся информационным показателем.

`/healthz/liveness` проверяет локальный consumer без доступа к хранилищу.
Сбой S3/PG даёт отрицательную readiness, но не вызывает рестарт через liveness.
`/health` — alias readiness. Вне Kubernetes readiness нужно вызывать периодически.
[Настройки и поведение проб](docs/task-store.md#heartbeat-last_modified-и-kubernetes-пробы).

Ожидающие `QUEUED` и уже завершённые задачи проверка таймаута не меняет. Просроченные
задачи не возвращаются в очередь автоматически: новую попытку создаёт Airflow
с новым ключом. После `FAILED` прежний физический выходной путь снова доступен
для новой заявки после очистки. Если все поды остановлены или очередь недоступна,
фиксация `FAILED` произойдёт после восстановления доступа обработчика readiness.

Поздние прогресс и завершение старой задачи не отменяют `FAILED`.
Worker проверяет состояние задачи перед записью следующего чанка; при потере
владения или завершённой задаче прекращает работу. Старый task_id никогда
не используется для новой попытки.

**Ограничение одинакового физического пути:** таймаут не доказывает остановку
процесса и не отменяет уже отправленный PUT в S3. В случае сетевой паузы
старый PUT может завершиться после того, как Airflow очистил путь и начал
повтор. Проверки worker и CAS очереди уменьшают риск, но не дают строгой
изоляции результатов. При доступе только к S3 и записи попыток в один путь
эта схема остаётся best-effort. `FAILED` по таймауту означает решение проверки таймаута,
а не подтверждение отсутствия старых операций записи.

SIGTERM/SIGINT немедленно устанавливает локальный сигнал остановки, сохраняя
штатный handler Uvicorn. Под не забирает новые задачи. Worker проверяет сигнал
до и после каждого GPU-батча, между чанками и перед публикацией `_SUCCESS`.
При обнаружении сигнала сохраняется `FAILED` с причиной `pod_shutdown`;
обычная отмена через API по-прежнему даёт `ABORTED`. Уже начатая операция GPU
или S3 завершается перед проверкой. Если `_SUCCESS` уже опубликован, worker
пытается сохранить `DONE`, а не пересчитывает результат.

Helm задаёт `terminationGracePeriodSeconds: 120`; значение настраивается
в `values.yaml`. При SIGKILL, OOM или недоступном S3 worker может не успеть
сохранить итог: задача завершится по таймауту при readiness. Таймаут задачи должен
учитывать сетевые задержки и рассинхронизацию часов подов.

## Хранилище TaskStore

`TaskStore` содержит только логику очереди. Физическое хранение выбирается через
`task_store.backend: s3` или `pg` в YAML. Backend получает подключение из ENV.
S3 хранит один JSON; PostgreSQL хранит каждую задачу отдельной строкой и не удаляет
историю по retention. Модель состояния находится в `app/tasks/types.py`.

[Настройки Helm, DDL и контракт backend](docs/task-store.md).

### S3 и CAS

Системный JSON содержит `revision` и словарь `tasks`. Для любого изменения:

1. GET возвращает содержимое и ETag одного объекта.
2. Код изменяет актуальное состояние в памяти.
3. PUT с `If-Match` сохраняет новую версию. После `409/412`, временной ошибки
   сервера или потери ответа операция перечитывает состояние и повторяет
   изменение с ограниченным сроком ожидания.
4. При неизменившемся состоянии PUT не выполняется.

Счётчик `revision` увеличивается при каждой записи, поэтому очистка не
возвращает содержимое к прежней версии. Захват фиксирует `RUNNING`, под и
уникальный идентификатор процесса. Владелец меняет прогресс и итог своего расчёта; readiness может
завершить просроченную задачу как FAILED. Потерянный ответ на захват восстанавливается чтением владельца.
Один consumer на под последовательно запускает worker; старейшая доступная
задача выбирается по `created_at` и `task_id`.

В вашем S3 `If-Match` работает без обрамляющих кавычек. Это явно задано
как `strip_etag_quotes: true` в YAML. Для сервера со стандартным форматом
можно задать `false`.

При старте под читает объект; если отсутствует — создаёт пустой JSON с
`If-None-Match: "*"`. При конкурентном старте победитель создаёт файл,
остальные читают уже существующий. **S3 должен поддерживать и условное
создание.** Безусловного fallback нет. Ошибка доступа, пустой JSON или
повреждённая структура не приводят к перезаписи очереди. Отсутствие объекта
во время работы тоже не трактуется как пустая очередь.

Readiness очищает историю завершённых задач раз в `cleanup_interval_sec`,
в том числе во время инференса. Записи старше `retention_months` удаляются из JSON
через CAS; месяц равен 30 суткам. Ожидающие и незавершённые задачи не удаляются.
Предел `max_pending_tasks` относится ко всем незавершённым задачам.
Очередь и история читаются и записываются целиком: схема рассчитана на
небольшое число подов и длительные расчёты. Версии объектов при включённом
S3 versioning требуют отдельной политики хранения на стороне хранилища.

## Конфигурация и logger

При startup для каждой модели вызывается `download_model_artifacts` из
`app/models/artifacts.py`. Пока это заглушка с записью через общий logger:
используются заранее размещённые локальные файлы. Реальное скачивание через API
model registry запланировано в [MODEL-002](docs/backlog.md).
Startup хранит только ModelSpec. Worker после claim создаёт pipeline и загружает
веса; после каждой задачи вызывает close до освобождения слота. Ошибка close
останавливает под и readiness, сохраняя исходный статус задачи.

В YAML настроены `fmcd_credit_cards` и `fmcd_debet_cards` с общим backend
`fmcd_cc_dc`, а также `fmcd_invest`. INVEST выполняет CatBoost с калибровкой,
preprocessing и нейросетевой stacking по исходным признакам из Parquet.
Ключи INVEST — `counterparty_id`, `report_dt`; комплект файлов и порядок
размещения описаны в [инструкции INVEST](app/models/backends/fmcd_invest/utils/README.md).
`device`, `infer_batch_size`, `parquet_read_chunk_size` задаются на каждую модель.
Для карт локальный комплект состоит из `model.pth`, `schema.json`,
`calibrators.json`, `freq_encoding.parquet`; model.json не нужен.

Препрод разворачивается с нуля. Переходные настройки и совместимость
с прежней архитектурой не реализуются.
Подробнее: [MODEL-001](docs/model-bundle-implementation.md).

Исходники движков находятся в `app/models/backends/<backend>/`:
`runner.py` содержит наследника ModelBundle, а в `utils/` лежат все
дополнительные функции, модельные классы и их подпакеты. Общий код API/worker отделён
от зависимостей движка. [Структура backend](app/models/backends/README.md).

Содержимое прежнего корневого `fmcd/` из рабочего сервиса нужно разместить в
`app/models/backends/fmcd_cc_dc/utils/fmcd/`, приведя внутренние импорты к новой
структуре. Backend использует прямые импорты этого пакета, без aliases.
Исходники моделистов в этом workspace не предоставлены.

`configs/models.yaml` — единственный источник настроек моделей, инференса,
и очереди. В коде нет дублирующих значений по умолчанию
для этих полей и нет переопределений `TASK_STORE_*`. Отсутствующее поле
или неверный интервал останавливает запуск.

Все параметры подключения S3 читаются напрямую из обязательных ENV:

| ENV | Значение |
| --- | --- |
| `S3_ENDPOINT_URL` | URL S3 |
| `S3_ACCESS_KEY` | Access key |
| `S3_SECRET_KEY` | Secret key |
| `S3_BUCKET_IN` | Входной бакет |
| `S3_BUCKET_OUT` | Выходной бакет с системным JSON |
| `S3_REGION` | Регион, например `us-east-1` |
| `S3_USE_SSL` | `true/false` или `1/0` |
| `S3_VERIFY_SSL` | `true/false` или `1/0` |

При `S3_VERIFY_SSL=false` сервис один раз при старте пишет через `logger.warn`,
что проверка TLS-сертификата S3 отключена. Повторяющиеся `InsecureRequestWarning`
от urllib3 подавляются в процессе; остальные категории предупреждений не отключаются.
При `S3_VERIFY_SSL=true` сервис не устанавливает этот фильтр.

`POD_NAME` задаёт имя пода; без него используется hostname.
Модели карт сохраняют `customer_mdm_id` и `partition_report_dt` из
`models[].id_cols`. Выбранный в YAML device не заменяется на CPU при
отсутствии CUDA: ошибка обнаруживается при load в worker и завершает задачу как FAILED.

`setup_logging()` получает существующий объект `logger` из
`dadm_functions.logger`; lifespan передаёт его в очередь, worker, загрузку
моделей, S3-клиент и API. Сервис использует только `info(message)`,
`warn(message)` и `error(message)`, всегда с одной готовой строкой.
Traceback исключений добавляется в текст `error`; `exc_info`, `exception`,
`warning`, `debug`, `setLevel` и handlers не используются.
Формат и вывод логов настраивает библиотека `dadm-functions`; секции
`logging` в YAML сервиса нет. Логи сторонних библиотек сервис не перенастраивает.

Для рабочего запуска требуется пакет `dadm-functions==0.5.5` из вашего
пакетного репозитория. В тестах используется строгий logger с тем же
интерфейсом, установка внутренней библиотеки для тестов не требуется.

## Добавление backend и модели

Backend реализует pipeline, а модель задаёт его настройки и артефакты. Несколько
моделей могут использовать один backend, как `fmcd_credit_cards` и `fmcd_debet_cards`.

### Новый backend

1. Создайте пакет `app/models/backends/my_backend/` с `__init__.py`, `runner.py`
   и пакетом `utils/`. Дополнительные классы, preprocessing и функции загрузки
   размещайте в `utils/`. Зависимости добавьте в корневой `requirements.txt`
   и согласуйте с версиями корпоративного образа в `Dockerfile`.
2. В `runner.py` реализуйте `NEWRunner`, наследующий
   [ModelBundle](app/models/contracts.py). Конструктор принимает `(spec, logger)`
   и сохраняет их через `super().__init__(spec, logger)`; загрузку весов выполняйте
   в `load()`. Этот метод также задаёт `required_columns` и `output_columns`
   без колонок ключей `spec.id_cols`.
3. Реализуйте `predict_batch(frame, check_shutdown)`: возвращайте DataFrame
   с ключами `spec.id_cols` и колонками результата `output_columns`, по одной строке
   на входную, сохраняя порядок строк и значения ключей. Не изменяйте входной frame.
   Вызывайте `check_shutdown()` между дорогими стадиями pipeline.
4. Реализуйте идемпотентный `close()`, освобождающий ресурсы даже после частичной
   ошибки `load()`. Worker создаёт новый экземпляр на задачу и вызывает `close()`
   в `finally`. Для логирования используйте переданный `self.logger`:
   `info(message)`, `warn(message)`, `error(message)` с одной готовой строкой.
5. Добавьте запись в `BACKENDS` в [registry.py](app/models/registry.py):

   ```python
   "my_backend": "app.models.backends.my_backend.runner:NEWRunner",
   ```

   Значение имеет формат `путь.к.модулю:ИмяКласса`. Сохраняйте ленивый импорт:
   не импортируйте runner или библиотеки модели в registry и общий код API.
6. Добавьте модель в конфигурацию по инструкции ниже. Проверьте контракт pipeline,
   сохранение ключей и порядка строк, отмену и повторный `close()`, включая случай
   ошибки загрузки.

### Новая модель

1. Выберите зарегистрированный backend. Если он поддерживает нужный pipeline,
   менять registry и создавать новый runner не требуется.
2. Разместите артефакты в каталоге, доступном каждому поду. Автоматическое скачивание
   пока не реализовано. Набор файлов определяется backend; для `fmcd_cc_dc` нужны
   `model.pth`, `schema.json`, `calibrators.json` и `freq_encoding.parquet`.
3. Добавьте элемент в существующий список `models` в
   [configs/models.yaml](configs/models.yaml), например для нового комплекта карт:

   ```yaml
   - name: "fmcd_cards_v2"
     backend: "fmcd_cc_dc"
     artifacts_dir: "artifacts/cards_v2"
     id_cols: ["customer_mdm_id", "partition_report_dt"]
     device: "cuda"
     infer_batch_size: 500
     parquet_read_chunk_size: 5000
     options: {}
   ```

   `name` должен быть уникальным: именно его клиент передаёт как `model_name`.
   Все показанные поля, кроме `options`, обязательны. Размеры batch/chunk должны
   быть положительными целыми числами, `id_cols` — непустым списком уникальных
   имён колонок. Относительный `artifacts_dir` считается от рабочей директории
   процесса. Специфичные параметры backend передавайте через `options`,
   не дублируя общие поля `ModelSpec`.
4. Перезапустите сервис с обновлённым YAML; в Kubernetes обновите образ с кодом
   и зависимостями при необходимости и передайте конфигурацию через
   `--set-file serviceConfig=configs/models.yaml`, как в разделе запуска ниже.
   Настройки читаются один раз при startup.
5. Отправьте `POST /infer` с новым `model_name`, подготовленным входным parquet
   и отдельным выходным префиксом. Дождитесь `DONE` через
   `GET /tasks/{task_id}/status` и проверьте колонки, ключи и число строк результата.
   Успешный startup сам по себе не проверяет загрузку весов и работу pipeline.

## Запуск и проверки

```bash
pip install -r requirements.txt
python main.py
```

Для тестов очереди, конфигурации, API и worker без GPU:

```bash
pip install -r requirements-test.txt
python -m unittest discover -s tests -v
ruff check app airflow_operators scripts tests main.py
ruff format --check app airflow_operators scripts tests main.py
```

Тесты используют S3 с атомарным CAS в памяти и моделируют конкурентные поды,
потерю ответа PUT, одновременную инициализацию, отмену, повторные запросы
и ошибки worker. Они не заменяют проверку конкретного S3-сервера и GPU-образа.
Артефакты из `artifacts/credit_cards/` и `artifacts/debet_cards/` и пакет моделистов
в `app/models/backends/fmcd_cc_dc/utils/fmcd/` необходимо предоставить для
запуска настоящего инференса.

Helm монтирует тот же YAML, переданный целиком:

```bash
helm upgrade --install fmcd-inference deploy/helm \
  -f deploy/helm/values.yaml \
  --set-file serviceConfig=configs/models.yaml
```

В `values.yaml` остаются параметры Kubernetes, образа и ENV подключения S3.
Настроек моделей и очереди там больше нет. Изменение YAML обновляет checksum
Deployment. Стратегия `Recreate` заменяет поды Deployment при обновлении.
Препрод разворачивается с нуля; перенос состояния прежней архитектуры не требуется.

## Утилизация ресурсов задач

При `calc_utilization=true` в запросе infer worker раз в секунду снимает CPU/GPU в %,
RAM/GPU_RAM в % и МБ. По умолчанию сбор выключен. Статистика min/max/mean/median
и число измерений считаются в памяти и выводятся в общий logger после close модели.
В TaskStore и ответе статуса статистики нет. В Airflow используется
`GPUModelInferenceOperator(calc_utilization=True, ...)`.
[Единицы и область измерения](docs/task-utilization.md).

## Рабочий образ и зависимости

Рабочий образ собирается корневым `Dockerfile`; он задаёт версии зависимостей.
`requirements.txt` и Poetry согласованы с ним. `main.py` запускает порт 8080
из `/app`; Helm монтирует конфигурацию в `/app/configs`.
`deploy/Dockerfile` закомментирован и не используется.
Пакеты для будущих pipeline в Dockerfile закомментированы до их подключения.

Spark обеспечивает одинаковые схемы входных parquet. `partition_report_dt`
в S3 остаётся обычной колонкой, хотя исходная Hadoop-таблица партиционирована по ней.
Отсутствующий входной шард завершается FAILED: входных данных нет.
